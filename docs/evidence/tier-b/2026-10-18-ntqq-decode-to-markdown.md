# QQ NT 聊天记录 → Markdown：定位、解密、解析与导出

> **类型**：Tier B 可行性 spike（对应 `Plan.md` 风险项 R-08、`requirement.md` REQ-006/REQ-008）
> **日期**：2026-10-18
> **结论**：在 QQ 9.9.33（Windows x64）上，把**全部**本地聊天记录转换为 Markdown 可行，已完成端到端验证。
> **脱敏**：本文不含任何真实消息、昵称、QQ 号、密钥或本机绝对路径；示例统一用 `<UIN>` / `<user>` 占位。

---

## 1. 结论摘要

| 项目 | 结果 |
| --- | --- |
| 数据库定位 | `%USERPROFILE%\Documents\Tencent Files\<UIN>\nt_qq\nt_db\`（可被客户端改到别的盘） |
| 容器格式 | `1024 字节 NTQQ 自定义头` + `N × 4096 字节 SQLCipher 页` |
| 解密 | 需 16 字符密钥；剥头后按 SQLCipher 参数解密，可用纯 Python 离线完成 |
| 密钥获取 | 官方逆向脚本（静态定位 + 调试器断点），**必须关闭 QQ 后重新登录一次** |
| 消息解析 | `c2c_msg_table` / `group_msg_table`，正文是 `[40800]` 的 protobuf Element 列表 |
| 导出 | 一次跑通：34 个会话 / 2234 条消息，含图片、文件、卡片、引用、表情 |
| 只读性 | 全过程只读复制数据库文件，未修改客户端任何数据 |
| 复用性 | 换机器只需“装 QQ → 取 key → 跑脚本”，但**密钥与版本强绑定**，不能跨机复用 |

一句话：**技术上完全可行，但密钥获取是唯一强耦合环节，也是产品化时最需要设计的一环。**

## 3. 数据定位

默认路径（每个账号一套）：

```
C:\Users\<user>\Documents\Tencent Files\<UIN>\nt_qq\
├── nt_db\                 ← 数据库（全部加密）
│   ├── nt_msg.db          ← 私聊 + 群聊消息
│   ├── profile_info.db    ← 好友资料、昵称
│   ├── group_info.db      ← 群列表、群成员、群名片
│   ├── emoji.db / files_in_chat.db / ...
│   └── *.db-wal, *.db-shm
└── nt_data\
    ├── Pic\<yyyy-mm>\Ori\<md5>.<ext>     ← 图片缓存
    └── File\                              ← 文件缓存
```

定位要点：

1. 客户端可以把 `Tencent Files` 指到别的盘（`requirement.md` 记录过 `D:\QQ聊天记录\Tencent Files`），不能硬编码。
2. 一个 `Tencent Files` 下可能有多份 `<UIN>`，需按账号分别处理。
3. `QQ.exe` 运行时会同时持有主库与 WAL 句柄；**不要边跑边读**，先做一致性快照。

## 4. 数据库容器格式

所有 NTQQ 数据库（实测 21 个）共用同一容器：

```
offset 0x00 : "SQLite header 3\0"     ← 伪 SQLite 魔数（真 SQLite 是 "SQLite format 3\0"）
offset 0x10 : 伪头部字段（页大小等字段被写乱，普通 SQLite 打不开）
offset 0x20 : "QQ_NT DB"              ← 标记
offset 0x2A : protobuf 元数据
              ├─ field 2 : 128 字节 ASCII hex（64 字节二进制）
              ├─ field 3 : "1.1.0.1"        ← codec 版本
              ├─ field 4 : "HMAC_SHA1"      ← 头部声明的 HMAC 算法
              └─ field 5 : varint
offset 0x400: 加密页开始（每页 4096）
```

**关键不变量**：`(文件长度 − 1024) % 4096 == 0`。本次 21 个库全部成立，可作为“剥头后页对齐”的自检条件；不成立就说明头部长度或页大小变了，应立即失败而不是继续。

加密参数（剥掉前 1024 字节后交给 SQLCipher）：

| 参数 | 值 | 说明 |
| --- | --- | --- |
| `cipher_page_size` | 4096 | 必须在 `PRAGMA key` **之前**设置 |
| `kdf_iter` | 4000 | |
| `cipher_hmac_algorithm` | `HMAC_SHA1` | 头部写的是 SHA1；上游记录 2024-12 起改为 SHA512 |
| `cipher_kdf_algorithm` | `PBKDF2_HMAC_SHA512` | 与头部 `1.1.0.1` 对应 |

> 实践建议：把 `(iter, hmac, kdf)` 做成候选列表，逐个试到 `SELECT count(*) FROM sqlite_master` 成功为止，避免死记某一版的参数。

## 5. 密钥获取

密钥是 **16 字符**随机串，**每个账号、每台机器都不同**，不随安装包常量，也不能从数据库自身推导。

官方脚本原理：

1. **静态分析** `versions\<ver>\resources\app\wrapper.node`：搜索字符串 `nt_sqlite3_key_v2: db=%p zDb=%s` → 找引用它的 `lea` 指令 → 用 `.pdata` 异常目录反查所属函数 RVA。
2. **动态调试**：`CreateProcess(QQ.exe, DEBUG_ONLY_THIS_PROCESS)` → 在函数 RVA 下软件断点 → 登录触发建库 → 从寄存器 `R8` 读取 `pKey`。
3. 命中后打印 16 字符密钥，并**终止它启动的那个 QQ 进程**。

### 操作步骤（必须按序）

```powershell
# 1) 先做静态分析，确认当前版本还能定位到函数（不动 QQ）
powershell -ExecutionPolicy Bypass -File .\windows_ntqq_get_key.ps1 -NoDebugForKey -Verbose

# 2) 完全退出 QQ（脚本会自行拉起新进程，单实例机制会让它在 QQ 已运行时直接退出）
taskkill /F /IM QQ.exe /T

# 3) 动态取 key：弹出的 QQ 里完成登录
powershell -ExecutionPolicy Bypass -File .\windows_ntqq_get_key.ps1 -Verbose

# 4) 输出 “加密密钥: XXXXXXXXXXXXXXXX” 即成功
```

### 这一环的硬约束

- **必须关闭 QQ**：单实例互斥，不关则新进程秒退，永远等不到断点。
- **必须完成一次登录**：不登录不会打开 `nt_msg.db`，就不会调用取 key 的函数。
- **会打断当前会话**：脚本结束会 kill 掉它拉起的 QQ，用户需要重新登录。
- **版本敏感**：函数 RVA 随版本变化，脚本靠“字符串 → 交叉引用 → 异常目录”动态推导，因此**一般**能跨小版本工作（9.9.32 / 9.9.33 均验证），但大改版可能失效。

> 产品化视角：这一步**不能静默做**。REQ-006 要求“用户明确授权”，密钥获取必须是一次显式、可解释、可拒绝的动作；`hook`/注入类方案（如 WeQ）也应只作为研究路径，不作为默认路径。

## 6. 解密

```text
1. 复制 nt_msg.db、nt_msg.db-wal、nt_msg.db-shm 到临时目录（快照）
2. 主库去掉前 1024 字节 → nt_msg_clear.db
3. 把 -wal / -shm 重命名成 nt_msg_clear.db-wal / -shm（否则丢最新数据）
4. 用 SQLCipher 打开，校验能读到 sqlite_master
5. sqlcipher_export() 导出为标准明文 SQLite
```

关键点：

- **WAL 必须一起带**：实测主库 2.3 MB + WAL 0.8 MB，只拷主库会丢最近消息。
- **参数顺序**：`cipher_page_size` → `key` → `kdf_iter` → 算法，顺序错了会报 `hmac check failed for pgno=1`。
- `profile_info.db`、`group_info.db` 用**同一把钥匙、同一组参数**，一次解三个。

失败特征对照：

| 现象 | 原因 |
| --- | --- |
| `file is not a database` | 没剥头，或用了普通 SQLite 而非 SQLCipher |
| `hmac check failed for pgno=1` | 密钥错 / 参数错 / 页大小错 |
| 能开库但表为空 | WAL 没带上，或剥头后页偏移错 |

## 7. 消息解析

### 7.1 两张主表

`c2c_msg_table`（私聊）与 `group_msg_table`（群聊）**列结构完全相同**：

| 列 | 含义 | 备注 |
| --- | --- | --- |
| `[40001]` | msgId | 雪花 ID，**高位不是消息时间**（见 7.4） |
| `[40003]` | msgType | 消息大类型（含系统消息码） |
| `[40011]` | msgSeq | 会话内序号 |
| `[40020]` | 发送者 uid | `u_xxx` 形式 |
| `[40021]` | 会话标识 | 私聊=对方 uid；群聊=群号 |
| `[40033]` | 发送者 QQ 号 | 本人消息即本账号 |
| `[40050]` | 消息时间戳 | 秒级；可能为 0 |
| `[40058]` | 当天 0 点时间戳 | 可能为 `-1` |
| `[40090]` | 群名称缓存 | **不可靠**，可能写入公告/广告文本 |
| `[40093]` | 发送者群昵称 | 常为空 |
| `[40800]` | 消息体 | protobuf，可能为 NULL |

### 7.2 昵称与群名

| 来源 | 用途 | 字段 |
| --- | --- | --- |
| `nt_uid_mapping_table` | uid → QQ 号 | `[48902]` → `[1002]` |
| `profile_info_v6` | 好友昵称 | `[1000]` uid、`[1002]` uin、`[20002]` 昵称 |
| `group_list` | **权威群名** | `[60001]` 群号、`[60007]` 群名 |
| `group_member3` | 群名片/昵称 | `[60001]`、`[1000]`、`[64003]` 名片、`[20002]` 昵称 |

> 教训：群名优先取 `group_list`，`[40090]` 只作兜底。实测 `[40090]` 里出现过广告文案，直接当群名会污染文件名。

### 7.3 消息体（Element）

`[40800]` 是一个 wrapper，内部是**扁平化**的元素列表：`45002` 开启一个新元素并给出类型，后续 `45xxx/47xxx/48xxx` 字段都归属该元素。

| `45002` | 类型 | 主要字段 |
| --- | --- | --- |
| 1 | 文本 | `45101` 正文 |
| 2 | 图片 | `45402` 文件名、`45406`/`45408` 摘要、`45802` 服务端参数 |
| 3 | 文件 | `45402` 文件名、`45403` 本地路径（`::NTOSFull::` 前缀）、`45405` 大小 |
| 5 | 视频 | `45402`/`45422` 文件名 |
| 6 | 表情/小表情 | `47601` 表情 ID、`47602` 名称 |
| 7 | 引用回复 | `47423` 内嵌 protobuf，field 9 = 被引用文本 |
| 8 | 灰条/系统提示 | `45003` 子类型、`48214` HTML/XML、`485xx` 结构化字段 |
| 10 | 卡片消息 | `47901` JSON（小程序/公众号） |
| 11 | 商城表情 | `80900` 名称 |
| 16 | XML 消息 | `48602` XML，取 `<title>` |

### 7.4 时间戳陷阱（重要）

- 首选 `[40050]`；为空时用 `[40058]`。
- **`msgId >> 32` 不是消息时间**，而是**批量同步时间**。实测 2204 条有效样本中 1497 条偏差 > 2 分钟，P95 偏差 17,280,000 秒（200 天）。用它兜底会把消息放错日期。
- 两者都不可用时，正确做法是**按会话内 msgId 顺序继承最近一条已知时间**（本次 30 条无时间戳消息即按此处理）。

### 7.5 媒体关联

- 图片缓存路径：`nt_data\Pic\<yyyy-mm>\Ori\<md5>.<ext>`，缩略图在 `Thumb\`。
- 用元素的 `45406`/`45408` 十六进制摘要匹配缓存文件名主干即可命中。
- **只能命中仍在本机的缓存**：本次 179 个图片元素中 49 个可链接、130 个已过期，必须如实标注“未缓存”，不要伪造链接。

## 8. 导出 Markdown 结构

```markdown
# <会话名>

- 类型：群聊
- 会话 ID：`<群号或 uid>`
- 消息数：N
- 时间范围：YYYY-MM-DD HH:MM ~ YYYY-MM-DD HH:MM

## 2026-08-19

**12:35:01 · <发送者>**

> 正文按引用块输出，多行自动续行
```

约定：

- 每会话一个文件，`index.md` 汇总；文件名做非法字符清洗与长度截断。
- 无正文的消息（系统消息/已撤回）保留占位 `*[系统消息／已撤回，本地无正文；type=N]*`，**不静默丢弃**——否则消息总数对不上，无法判断是解析失败还是本来没有。
- 媒体用相对路径 + `<...>` 包裹（路径含空格），保证在仓库/编辑器里可点开。

## 10. 鲁棒性与失效模式

| 环节 | 依赖 | 失效表现 | 降级/处置 |
| --- | --- | --- | --- |
| 数据定位 | 默认路径 | 找不到库 | 支持自定义 `Tencent Files`；遍历 `<UIN>` 子目录 |
| 容器格式 | 1024B 头 + 4096 页 | 页不对齐 / 魔数不符 | 立刻失败并报错；用不变量做自检 |
| 密钥 | 版本相关函数 RVA | 脚本找不到函数 / 长时间等不到断点 | 升级脚本；改用 WeQ（注入，无需重启）；用调试器手工定位 |
| 密钥 | QQ 必须退出 | 新进程秒退，脚本一直等待 | 先 `taskkill`；提示用户会中断会话 |
| 密钥 | 必须登录 | 断点不触发 | 提示扫码/密码登录 |
| 解密参数 | `(iter, hmac, kdf)` | `hmac check failed` | 候选列表轮询（SHA1/SHA512、4000/64000） |
| WAL | 需 `-wal/-shm` | 丢最近消息 | 快照时三件套一起拷 |
| 消息体 | 扁平 Element 结构 | 出现未知类型 | 输出 `[未识别元素 N]` 并计数，不吞掉 |
| 时间戳 | `40050`/`40058` | 0 或 -1 | 相邻消息继承；**禁用 msgId 高位** |
| 群名 | `group_list` | 群不在 `group_list` | 回退 `[40090]`，标注可能不准 |
| 媒体 | 本地缓存 | 已清理 | 标注“未缓存”，保留原文件名 |
| 版本升级 | 表结构 / 字段号 | 解析结果为空或错位 | 以 `sqlite_master` + 抽样断言做启动自检 |

**最大的结构性风险**：整套解析依赖“字段号即语义”（`40020`/`40800`/`45101`…），这是逆向结论，不是公开契约。客户端一旦调整字段编号，解析会在不报错的情况下产出错乱内容。因此**必须**有抽样校验（例如“文本消息不应为空”“群消息的 `[40021]` 应命中 `group_list`”），否则宁可判为不支持。

## 11. 对产品的结论（Tier B 适配器）

1. **可行性成立**：QQ NT 的本地库可只读解密并完整还原为结构化数据，足以支撑 `REQ-006`。
2. **架构建议**：`快照 → 离线解密 → 解析 → 标准化 DTO`，客户端只被读一次文件；解密与解析都不在查询路径上（与 `Plan.md` 的“独立索引 + 可替换适配器”一致）。
3. **版本适配器**：以 `(客户端版本, 头部版本串 1.1.0.1, cipher 参数)` 作为适配器键；启动时做“页对齐 + 抽样断言”健康检查，失败即降级 Tier A，绝不输出半成品。
4. **授权设计**：取密钥必须是一次显式动作（说明会重启客户端、会读取什么、不会上传什么），不能用 `hook`/注入做默认路径（AGENTS.md 禁止项）。
5. **不可承诺**：“所有版本零操作”“不解密就能读”都不成立；`requirement.md` 里 Tier B 标注为实验性是准确的。
6. **对目标版本的行动**：先在 9.9.29 上复跑本文第 9 节清单，把结果补进版本矩阵，再决定是否纳入实现。

## 12. 隐私与合规

- 本文与随附脚本**不含**任何真实消息、昵称、QQ 号、密钥或本机绝对路径。
- 密钥只存在于当次进程环境变量，不落盘、不入库、不进 Git。
- 运行时数据库、WAL、导出结果均被 `.gitignore` 覆盖（`*.db`、`*.db-*`）。
- 仅用于本机、本账号、本人授权的数据；不得分发他人聊天记录。
- 取密钥过程会短暂中断客户端会话，属于需要用户知情的操作。
