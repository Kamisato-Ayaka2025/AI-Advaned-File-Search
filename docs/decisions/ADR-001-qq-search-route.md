# ADR-001：QQ 模糊记忆与跨时间过程查找

- 日期：2026-10-18；状态：选定实施路线，未实现、未实测；参数在开发集校准。
- 范围：REQ-013、015–025、028–031；QQ 解码已有队友实验依据，不重新研究取钥，结构化输入仍依赖 A-05。
- A/@Kamisato-Ayaka2025：契约、关系存储、受限调度、安全；B/@YuanKunlin：检索算子、LLM适配、评测；C/@Zhong-Yufeng：UI、构建与计时。
- 本文是 Plan.md 的实施细则，不修改 requirement.md 确认状态，不宣称通过任何软件 Gate。

## 1. 选定路线

多粒度本地混合召回 → 显式关系与上下文扩展 → 最多两轮 Agent 补查 → 原文证据回答。

Agent 负责提出下一批查询和判断缺哪类证据，程序负责权限、索引、预算、并发、停止和引用校验。不是让 Agent 扫描全库，也不是一次 top-10 就永久排除其他消息。top_k=10 仅限制 UI 首屏。

首版用 SQLCipher/SQLite + FTS5、bge-small-zh-v1.5、本地向量与回复邻接表。先不部署本地生成 LLM、全量生成摘要、完整 GraphRAG 或额外向量服务。模糊记忆可由 Embedding 先找到线索，不必每个查询都先等待远端生成模型。

| 备选 | 决策理由 |
|---|---|
| 全库输入长上下文模型 | 不采用：等待、输入成本和权限难控，能装下不保证找全 |
| 单次关键词/向量 top-10 | 留作评测基线，不能解决隔数周的解答 |
| 本地生成模型逐条筛选 | 不采用首版：新增资源成本，错误排除仍会漏证据 |
| 预先生成全库事件图 | 后置：预处理昂贵、自动关系可能错误，先使用真实回复关系 |
| 受限多轮检索 | 采用：已有线索驱动下一次查找，预算内尽量补齐过程 |

## 2. 索引：短片段负责召回，原消息负责证据

### 2.1 数据组织

- Message：保留 source/account/chat/message/sender ID、原文、seq、时间/精度、quote_of、解析状态；未知时间与空正文不删除。只索引文本/文件名，不 OCR。
- Parent：保留原计划的20–50条上下文容器，默认30条、重叠5条；窗口不代表同一事件。
- Retrieval child：parent 内约4–8条消息的小窗口，重叠1–2条；正文目标≤384 embedding tokens，含元数据不得超过所选模型上限。长消息按 tokenizer 再分块，保留原消息ID/字符区间；禁止静默截断尾部。
- FTS 索引消息分词副本及文件名，向量索引 child；命中后再读取 parent/原消息。以 message_id/字符区间去重，不能把重叠当多条独立证据。
- `message_edges(from_id,to_id,type,provenance,revision)` 保存显式回复/引用及反向索引；丢失目标标 unresolved。相似文本、同一参与者或时间接近仅是候选信号，不存为已确认事件关系。
- 错误码、项目名、URL、文件名可作精确检索键。“上次那个问题”“好了”不能单独证明对应哪个问题。首版无需全库 LLM 摘要，摘要若后加须关联原文ID，不作为最终引用。

### 2.2 更新与规模

新消息只更新受影响窗口和关系；模型/切段/分词改变则切新 index_revision。SQLite与向量原子发布，运行中请求固定数据快照。

当前2234条实验样本/一万条验收，用加密SQLite保存向量、内存精确cosine作为基线。通过 `VectorIndex` 接口预留 hnswlib/HNSW；精确检索超过预算时才启用，Windows安装/打包需验证。

ANN过滤必须保持召回与权限：窄过滤集合可直接精确比较；大集合使用受控过采样与过滤，候选不足扩至预算上限后标 partial，不返回不满足硬过滤的数据。ANN recall@80 相对精确向量基线目标≥0.95，参数在开发集调，不能用测试集反复调参。

向量/ANN文件同样属于敏感派生数据；加密持久化、启动加载、崩溃残留、删除未过G5前，只能在合成数据上测试。不得为方便索引加载写明文临时副本。

一百万消息与向量数量V不同。512维float32的纯向量内存为 `V×512×4` 字节；V=一百万时约2.05GB，未包含图、模型、UI。故百万规模单独测V、token、总RSS、冷启动、导入与增量耗时；不能沿用一万条≤1GB/两分钟索引的承诺。分片/量化/磁盘索引按实际瓶颈另作决策。

## 3. 查询执行步骤

### S0 本地解析范围

显式账号/会话/日期限制为 hard_filters，用户“好像三月份”“可能是张三”为 soft_hints，不能误变硬过滤。权限及明确限制不可放宽，UI展示理解和覆盖范围。明确统计用SQL，不由模型估算。

### S1 并行召回，先显示原话

原查询并行取 BM25 top-80、向量 top-80，加精确实体/引用命中；去重后候选池最多200。FTS5 BM25较小分数更好；不同通道不直接相加原始分数，使用 `RRF=Σ1/(60+rank)`。

融合保留80个候选，按会话/时间/重复区间软多样性排序，避免同一问题重复描述挤走后续解答；精确引用不能因多样性被机械剔除。选12个seed，首屏显示top-10，其余保留本地调查状态。

### S2 本地关系扩展

取seed的parent、前后各10条；显式回复/引用双向最多2跳，新增最多120条并去重，超出返回truncated。时间再远的显式引用也可被找到，不受前后十条限制。

无显式引用时，用已发现错误码/项目名/方案词在全授权范围继续搜。原会话优先但不是唯一来源；同名不同项目分别保留候选。邻近上下文只供理解，不能自动判为同一事件。

### S3 受限 Agent 调查

精确查找可直接返回本地列表；普通问答至多一次生成。过程类问题进入下述流程：

1. 第一次决策读原问题及代表性证据，返回JSON：已知evidence_ids、missing_stages、最多3条补查query、需要展开的ID、action=search/finalize/clarify。只要求短依据，不要求长篇思考输出。
2. 程序校验schema、权限和ID，并行执行该批查询/展开。补查保留原问题与已确认实体，防止改写漂移；不能将模型猜测日期变成硬限制。
3. 默认一轮补查；关键阶段仍缺且预算允许时才进行第二轮。决策输入是证据表+新增原文，不反复回灌整段历史。
4. 最后一次调用生成答案。最多“两次决策+一次答案”共3次远端请求，不另外安排LLM自评/摘要链。首次可直接finalize，跳过补查。
5. 缺乏线索时最多澄清一次；不回答则返回候选和缺口，沿用REQ-023的待确认范围。

只允许 `search_batch`、`expand_messages`、`get_messages`。不允许任意SQL、文件读取或shell；聊天内容是数据，不能作为工具指令或发送授权。缺证据时不得无限尝试。

### S4 证据打包与回答

按“提出问题/尝试与反馈/解决方案/验证结果”组织证据，阶段可missing/not_applicable；不为凑齐过程编造。保留冲突与不同事件分支，不能只选最支持某个答案的文本。

每条结论绑定原消息ID和字符区间；原文、发送者、时间从库读取。程序检查ID/权限/revision/引文一致；语义是否真正支持结论由人工评测判断，ID存在不是支持证明。

结果含 answered/partial/not_found/ambiguous、missing_stages、coverage、budget_exhausted。只说“当前已索引范围内未找到”；无可追溯关联的“好了”保留不确定，不拼接成确定结论。

## 4. 上下文、调用和时间预算

以下为初始配置，不是已验证SLA。

| 项目 | 标准模式预算 |
|---|---|
| 第一次/第二次决策输入 | ≤4k/6k tokens，含系统指令、schema、问题和证据 |
| 决策输出 | 各≤512 tokens |
| 最终回答输入/输出 | ≤12k/1500 tokens |
| 全流程输入 | 累计≤24k tokens，重复发送也计算 |
| 远端调用 | ≤3次，错误重试也占次数与剩余时间 |
| 补查 | ≤2轮，每轮≤3个并行查询；原始S1另计 |
| 标准调查截止 | 30秒机器处理时间，到时返回已有证据/partial |

采用实际tokenizer；不可用则校准保守估算并预留余量。实际模型窗口更小时降低预算。上下文窗口与累计token量分别限额，不能通过重复请求规避。

只有能为最终答案预留约12秒才发起第二次决策，否则直接整理现有证据。调用超时不得大于剩余预算；deadline取消网络流和后续任务。隐藏推理耗时不可精确预测，不把输出token上限当时间保证。DeepSeek模型/支持参数仍需账号验证，不擅改原需求默认模型名；普通JSON即可执行该决策流程，不强依赖native tool calling。

### 授权与缓存

先本地检索，再预览发送内容。每次向Planner或答案模型发送查询/原文，仍走SendPlan并校验payload hash；补查得到的新原文超出旧授权范围，必须再预览/同意。可按轮批量预览，不授权任意未来内容；拒绝/撤回即停云端并保留本地结果。

分别记录机器处理时间和含用户同意等待的总耗时。30秒不计用户阅读时间，但UI不得隐瞒实际总等待。

缓存绑定 query、hard_filters、授权数据范围、index_revision、模型/分词版本；命中前重查权限/撤回状态，删除清缓存。缓存上下文不能绕过外发同意。

## 5. 本地模型取舍

必需：本地bge-small-zh-v1.5，验证ONNX/FastEmbed加载、tokenizer、池化与归一化；不让Embedding硬淘汰所有低分消息，后续可再次查询。

默认重排用RRF、去重、元数据软匹配和阶段/时间多样性。模型判断前的阶段词只作弱标签，例如“试过/解决/验证”，不作为阶段事实；标签缺失不能硬排除候选。可选 `BAAI/bge-reranker-base` 只处理最多24个融合候选，做消融后再启用；CPU时延和内存未通过时关闭，不因base名称就宣称满足1GB预算。重排只能改善已召回内容，不能补回没找到的解答。

不把本地生成模型作为首版前置依赖；若基线与补查仍无法达到质量门槛，再评估模型升级或本地辅助摘要。

## 6. 可执行分工与契约

| 文件/接口 | 主责 | 责任 |
|---|---|---|
| `contracts/search.py` | A，B/C评审 | SearchSpec/Candidate/EvidenceBundle/InvestigationDecision/SearchOutcome |
| `storage/relations.py` | A | 显式关系、数据版本、来源；不写推断为事实 |
| `retrieval/hybrid.py`、`vector_index.py`、`context.py` | B，A审关键边界 | 批量召回、排序、上下文读取，遵守传入限制 |
| `application/search_coordinator.py` | A（高级） | 状态机、时间/token/轮次预算、授权、取消与快照 |
| `llm/search_decision.py`、`answer.py` | B | JSON决策/回答适配，不自行扩大权限或重试 |
| `ui/search_status.py` | C | 首批原话、进度、缺口、预览与取消 |
| `tests/evaluation/` | B，A复核 | 标注问题、阶段证据、相似事件干扰与基准 |

源码路径均相对 `src/original_words/`，tests在根目录。SearchSpec区分硬过滤/软线索/意图/预算；EvidenceBundle含revision、message_ids、char_spans、stage_candidates、edge_provenance、missing_stages、coverage、truncated；SearchOutcome附引用、状态、耗时、调用数、累计token和stop_reason。

状态机：LOCAL_RETRIEVE → LOCAL_EXPAND →（LOCAL_RESULT 或 CONSENT → DECIDE → SEARCH_BATCH，至多两轮）→ CONSENT_IF_NEEDED → ANSWER → VALIDATE → DONE/PARTIAL。任意状态可CANCEL/REVOKE/TIMEOUT，新请求使旧结果失效。

## 7. 验收：正确与快速必须一起测

### 7.1 固定问题集与对照

80题：20模糊记忆、20跨周/月过程、15相似项目干扰、10冲突/否定、10无证据、5未知时间/断引用。按事件划分20开发/60保留测试，同一事件改写不能跨组；参数仅在开发集调整。真实样例先授权脱敏，公共CI只用合成数据。

同语料、权限、模型、机器和调用/token上限比较：① BM25/工具搜索Agent，允许正常换词；② 单次混合top-10+邻域；③本路线。不能故意限制基线功能制造速度优势；原Plan的20题槽位、10题人工答案仍保留。

### 7.2 G7初始门槛（实施前由A确认参数）

- 初始候选macro recall@80≥0.95：有证据题按相关消息ID去重计算，负例不入分母；不是最终答案准确率。
- 跨时间阶段证据召回≥0.90：所需且确有标注证据的阶段中，EvidenceBundle覆盖的比例。
- 完整链成功率≥0.80：该题必要阶段都覆盖、引用支持且无跨事件误串；本无验证结果的题不能凭空补齐。
- 人工结论支持率≥0.95；引文ID/字符区间有效率100%；无证据题不得编造解决方案。
- 跨事件错误合并率≤0.05，按干扰题中错误拼接的查询比例统计；报告样本量，不把小集通过称为普遍准确率保证。
- 预算超限、权限越界、撤回后继续外发均为0。

### 7.3 性能目标与统计

一万条、模型热态、索引就绪、Windows SSD基准机器：首批本地证据p95≤1秒，本地扩展/证据包p95≤2秒；普通生成p95≤15秒、标准调查p95≤30秒为新增待测目标。原索引≤2分钟、RSS≤1GB保持不变。

REQ-029的首token≤5秒记录为生成请求发起后的API耗时；另报用户提问→首批证据→生成请求→首token→完整回答的时间，不能混淆起点。

每配置至少30次查询，冷/热、网络正常/失败分开，记录p50/p95/最大值、超时率、完整链成功率和各阶段耗时。强制30秒返回partial不算完整链成功；不得剔除失败或慢样本后宣称全部答案快速完成。

10万/100万消息另跑容量组，记录child数、索引大小、构建/增量/冷启动、RSS、ANN recall与业务质量；未通过不宣传百万级支持。本轮仅方案研究，没有运行模型/API/性能实验。

## 8. 实施顺序

| 阶段 | A | B | C | 出口 |
|---|---|---|---|---|
| SR0 | 冻结DTO/预算及8个合成跨时间事件 | 首批标注/基线查询 | mock原话与缺口UI | 可执行契约样例 |
| SR1 | child/parent、关系仓储与revision | 混合召回/批量扩展/计时 | 首屏原话、引用跳转、取消 | 本地链路与性能基线 |
| SR2 | 受限调度/授权复核 | JSON决策/回答、80题评测 | 补查与发送预览 | G7，不将SR1冒充完整过程能力 |
| SR3 | 按瓶颈评估ANN加密/容量 | ANN/可选重排消融 | 大规模进度/部署 | 扩展规模单独验收 |

SR0/SR1最小样例可并入六小时演示；SR2全评测与SR3另排期，不承诺六小时完成。QQ结构化适配与搜索mock并行，搜索方案不等待重新解码。

停止：两轮/预算耗尽、无新证据、重复同类查询或覆盖不足时返回partial与缺口。用户主动继续才开新预算，沿用证据状态但重新核对权限。

## 9. 一手依据（2026-10-18核对）

以下仅支持方法/工具能力，不能证明本项目性能。上述预算和门槛是本项目工程选择。

- [SQLite FTS5](https://www.sqlite.org/fts5.html)：全文/BM25排序。
- [BAAI bge-small-zh-v1.5](https://huggingface.co/BAAI/bge-small-zh-v1.5)：中文512维Embedding，具体token限制按锁定工件验证。
- [BAAI bge-reranker-base](https://huggingface.co/BAAI/bge-reranker-base)：query-document重排。
- [IRCoT原论文](https://arxiv.org/abs/2212.10509)：由中间线索继续检索的方法依据；这里输出结构化动作，不要求长思维链。
- [GraphRAG DRIFT](https://microsoft.github.io/graphrag/query/drift_search/)：关系扩展参考，不引入完整框架。
- [hnswlib](https://github.com/nmslib/hnswlib)：本地近似向量检索候选，Windows打包和安全持久化需验证。
